The core problem is that a failed request and a request whose *response* got lost look identical from your side.

Your retry logic sees a timeout, or a 502, or a dropped connection, and concludes "that didn't go through, try again." But a timeout tells you nothing about what happened on the server. The charge may have been fully processed and committed, and then the response got eaten on the way back — slow network, load balancer gave up, your HTTP client's deadline fired. You retry, the payment processor sees a brand new charge request, and it charges the card again. Twice the money, one order.

This is the fundamental thing about distributed calls: **you cannot distinguish "it didn't happen" from "it happened and I didn't hear about it."** Retrying is only safe if doing the thing twice is the same as doing it once.

That property is idempotency. `DELETE /users/42` is idempotent — delete it twice, still deleted. `POST /charges` is not, by default. Every call creates a new charge.

The fix is to make the operation idempotent by giving the server a way to recognize a retry as a retry. You generate a unique key *once*, before the first attempt, and send the same key on every retry of that same logical operation:

```
POST /v1/charges
Idempotency-Key: 7f3a9c1e-...   # generated once, reused on all retries
```

The server stores the key alongside the result. First time it sees the key, it processes the charge and records the outcome. Any subsequent request with that same key gets the *stored response* replayed back — no second charge. Stripe, Adyen, Square all support this; check the docs for the exact header name and how long they retain keys.

The part people get wrong: **the key must be generated by the caller, before the first attempt, and must not change between retries.** If you generate it inside the retry loop, or derive it from a timestamp, every attempt gets a fresh key and you're right back where you started. Tie it to the business operation — the order ID, the checkout session — not to the attempt.

A couple of things to sort out alongside it:

- Only retry on errors where a retry could plausibly help: timeouts, 5xx, connection resets. Don't retry a 400. A card decline is a definitive answer, not a transient failure.
- Use exponential backoff with jitter, and cap the attempts. Aggressive retries against a struggling processor are how you turn a blip into an outage.
- If you're persisting the charge on your side too, make that write idempotent as well — a unique constraint on the idempotency key in your own table is cheap insurance and will catch the case where your service crashes mid-flow.

And for the charges that already went out: those need reconciliation against the processor and refunds. The idempotency key fixes the future, not the past.
