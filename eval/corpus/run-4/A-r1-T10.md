I'm against the deletion, but I think you're right about the actual problem, and I don't want the pushback to bury that. A CI suite everyone ignores is worse than no CI — it costs time on every run and provides zero signal, and we've been living with that for months. Something has to change.

My objection is to the selection criterion. "Failed more than twice in the last month" doesn't select for *useless* tests, it selects for tests that touch the least stable parts of the system. Some of those are flaky tests over solid code. Some of those are solid tests over genuinely broken code that has been failing intermittently and telling us so. The proposal deletes both, and the second category is the one where deleting it means shipping the bug. We'd be turning our best early-warning signal into silence and calling it green.

The other thing that worries me: once "delete the test" is an accepted response to a failing test, it becomes the cheapest response to every failing test. Six months from now the suite is green because it's empty.

**What I'd do instead — quarantine, don't delete.**

Move the offenders out of the blocking suite into a separate lane that runs on the same schedule but doesn't gate merges. That gets you the thing you actually want, which is a green required check that means something, and it gets it this week. But the tests keep running and we keep the data.

Then, on the quarantined set:

**Triage each one before deciding anything.** Rerun it in a loop, ten or twenty times, against unchanged code. Deterministic pass means the test is fine and there's a real bug — that goes to the bug tracker at whatever priority it deserves, and it's the most valuable output of this whole exercise. Nondeterministic means it's genuinely flaky, and then you fix it or you cut it, having actually looked.

**Most flakiness has about four causes** and they're all fixable: real time (`sleep`, timeouts, anything asserting on wall clock), shared state between tests that only bites under a particular ordering or parallelism, unawaited async, and external dependencies that should be stubbed. None of these are mysterious. They're just nobody's job right now, which is the real issue.

**Delete with a reason, not with a count.** I'm completely fine deleting a test that turns out to assert on something we no longer care about, or that duplicates coverage elsewhere, or that tests an implementation detail we've since rewritten. That's good hygiene. The difference is that we deleted it because we understood it, not because a query returned it.

**Put a clock on it.** Quarantine with no deadline is deletion with extra steps — the list just grows and nobody looks at it. I'd say: each quarantined test gets an owner and two weeks. At the end of two weeks it's fixed, or it's deleted with a one-line note saying why. Cap the quarantine list size so it can't become a dumping ground.

Two more things that would help regardless:

- **Track flake rate as a number** so we're arguing about data instead of vibes. Most CI systems can report per-test pass rate; if ours can't, that's worth an afternoon.
- **Make the required check genuinely required.** The reason people ignore CI is that ignoring it has been free. Once the blocking suite is trustworthy, it should actually block.

I'd guess the real triage work here is a week of one person's time, not a quarter. And we'd come out with a green suite people trust plus a list of real bugs we currently don't know about. Happy to take the first pass through the list if it helps get it moving — the disagreement is about method, not about whether this needs fixing.
