I am against it, though I agree with the problem you are naming. A CI signal everyone ignores is worth nothing, and we should fix that. Deleting the failures fixes the color, not the signal.

The trouble is that "failed more than twice" mixes two very different tests together. Some are flaky — timing, shared state, test order, a real network call. Those tell you nothing and should go. Others fail because they are catching a real intermittent bug, the kind that shows up in production at 3am and takes a week to trace. Delete both and you have thrown away your only warning about the second kind.

There is also a ratchet problem. Once deleting a test is the accepted response to a red build, that becomes the cheapest fix available, and coverage erodes wherever the code is hardest to test — which is usually the code that most needs tests.

What I would do instead:

- **Quarantine, do not delete.** Move the failing tests to a separate suite that runs but does not block merges. The main suite goes green this week, and you keep the evidence.
- **Put a name and a date on each one.** Quarantine with no owner is deletion with extra steps. Give each test an owner and a two-week deadline to fix or delete with a written reason.
- **Triage before you touch anything.** Spend an afternoon on the list. My guess is most are one or two shared causes — a fixture that leaks state, a hardcoded sleep, tests that assume execution order. Fix the cause and a dozen tests go green at once.
- **Delete freely once you understand why.** A test that asserts something we no longer care about should go, and I will approve that PR happily. The rule is that we know what we are giving up.

Net: same green build, roughly the same effort, and we keep the tests that were actually earning their keep. Want to go through the failure list together this week?
