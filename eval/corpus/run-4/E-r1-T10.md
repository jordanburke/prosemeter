I'm against deleting them, but you're right about the underlying problem. A suite everyone ignores is worth less than no suite, because it costs time and buys no confidence. That part needs fixing.

Deleting is the wrong lever, though. "Failed more than twice" selects for two very different things. Some of those tests are flaky and prove nothing. Others are the tests that keep catching real bugs — they fail repeatedly *because* they're covering the code we break most. Delete by failure count and you can't tell which is which, so you lose exactly the coverage that's earning its keep. The suite goes green and the bugs still ship, only now nothing warns us.

Here's what I'd do instead, and it gets us to green just as fast:

1. **Pull the failure data** and sort each test into one of three buckets: fails intermittently on unchanged code (flaky), fails consistently (real bug or stale assertion), fails on shared setup (infrastructure).
2. **Quarantine the flakes**, don't delete them. Move them to a separate non-blocking job. CI goes green today, the tests stay on disk, and we keep the signal.
3. **Give the quarantine an owner and a deadline.** Each test gets a name and a date. Fixed or deleted by then, and deleting after investigation is completely fine — that's a decision, not a purge.
4. **Fix the consistent failures properly.** If the assertion is stale, update it. If it caught a real bug, we just found a real bug.
5. **Make the flakiness harder to reintroduce.** Most flakes trace back to a few causes: shared state between tests, real clocks, real network, and ordering assumptions. Fixing the pattern is usually cheaper than fixing the tests one by one.

One thing to add: an empty quarantine list should be the goal, and a growing one should be visible in standup. Otherwise quarantine becomes the same graveyard as deletion, just slower.
