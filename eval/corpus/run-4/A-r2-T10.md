I'm with you on the problem and against the proposed fix. A suite nobody trusts is worse than no suite — people rubber-stamp red builds, and then the one real failure sails through. That's a genuine emergency and I don't want to downplay it.

But "failed more than twice" doesn't select for flaky tests. It selects for *tests that found something*. Sorting by failure count puts three very different things in the same bucket:

- **Genuinely flaky tests** — timing assumptions, shared state between tests, real clock or network dependencies. These deserve to be fixed or deleted.
- **Tests covering genuinely unstable code.** These are failing because the thing they test is broken. Deleting them doesn't fix the code, it just stops telling you about it — and it will be the code around your most-touched, highest-risk paths, because that's what changes enough to break.
- **Correct tests with a bad harness underneath them.** One leaky fixture or a missing cleanup can make a dozen unrelated tests fail intermittently. Delete all twelve and the fixture bug survives to poison the next twelve.

The failure count doesn't distinguish these, and the second category is precisely the coverage you'd most regret losing. There's also a ratchet problem: once "delete it" is an accepted response to a red test, it becomes the cheapest response to every red test, and the suite erodes from the parts that matter most.

**What I'd do instead**, and I think we can get green faster this way than by arguing about the list:

1. **Quarantine, don't delete.** Move the offenders to a separate non-blocking job. CI goes green today — you get the outcome you're after, immediately — but the tests still run and we can still see them. Nothing is lost while we triage.
2. **Triage the quarantine list into the three buckets above.** My guess is it collapses fast — flaky tests cluster around a small number of root causes, usually shared fixtures, an unmocked clock, or test-order dependence. Fixing four things may clear thirty tests.
3. **Set a real expiry.** Anything still quarantined after, say, three weeks gets deleted for real, with a note saying what it covered. That keeps quarantine from becoming a graveyard, which is the failure mode of every quarantine system I've seen.
4. **Make deletion explicit and reviewed.** A PR titled "delete flaky test X because it asserts on wall-clock timing" is completely fine. A bulk delete by failure count isn't, because nobody's actually looked.

I'd bet real money that at least one thing on that list is a live bug. Want to go through the list together this afternoon? If it turns out to be thirty tests and three root causes, we can have this fixed rather than hidden by the end of the week.
