I'm against it as stated, but I think you're identifying a real problem and I don't want that to get lost.

The real problem: a suite people ignore is worse than no suite. If CI is red by default, nobody reads it, and the one time it goes red for a genuine reason it gets waved through with the rest. You're right that the current state is actively harmful and that doing nothing is not neutral.

Where the proposal breaks down is that "failed more than twice" doesn't separate the two populations you care about. That bucket contains:

- **Genuinely flaky tests** — timing assumptions, shared state between tests, real clocks, network calls, order dependence. These tell you nothing and should go or be fixed.
- **Tests that are correctly reporting a real intermittent bug.** A race condition in the code under test looks exactly like a flaky test from the CI dashboard. Deleting it doesn't fix the race, it just removes the only thing telling you about it — and by construction, these are concentrated in your most concurrent, most timing-sensitive, highest-stakes code. That's the failure mode that scares me: the filter is biased toward deleting the tests covering the code most likely to break in production.

You can't tell which is which from the failure count alone. Someone has to look.

**What I'd propose instead**, which gets you a green board this week without throwing away signal:

**Quarantine rather than delete.** Move every offender into a separate suite that runs, reports, but doesn't block merges. Board goes green immediately — you get the thing you actually want, today. The tests still run and still produce data, so nothing is lost.

**Put an expiry on the quarantine.** Two weeks, or a fixed budget of engineer-days. Anything not triaged by then gets deleted for real. Without this the quarantine becomes a permanent graveyard, which is your proposal with extra ceremony and I'd rather not pretend otherwise.

**Triage in priority order, not arbitrarily.** For each one, the question is "is the test wrong or is the code wrong?" Sort by what the test covers — payments, auth, and data integrity get looked at by a human; a flapping snapshot test of a tooltip gets deleted without ceremony. Most of them will genuinely be test bugs, and deleting those is fine. It's fine *because someone checked*, not because they failed twice.

**Then fix the intake.** Whatever process let 40 flaky tests accumulate will produce 40 more. Usually that's: no retry policy so flakes are invisible until they're endemic, or a culture where re-running CI is the normal response to red. Track flake rate as a metric and treat a newly-flaky test as a bug with an owner.

Honestly, I'd guess 80% of the list is safe to delete and you and I would agree on nearly all of it in an afternoon of triage. My objection is entirely to skipping the afternoon. Want to sit down with the list tomorrow and sort it?
