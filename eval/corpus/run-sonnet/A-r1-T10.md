I'd push back on this one. Deleting the tests fixes the dashboard, not the problem. A test that fails intermittently is telling you something is genuinely non-deterministic — usually either a real bug (race condition, unhandled async, shared state between tests) or a badly written test (relies on timing, ordering, or external state). Either way, deleting it doesn't fix that, it just makes the failure invisible instead of caught in CI. It tends to resurface later as a production incident, minus the diagnostic trail the test would've given you.

What I'd do instead:
- Triage each failing test into "real bug" vs. "bad test" — they need different fixes, and treating them as one group is how this problem started.
- Quarantine rather than delete — mark them skipped or flaky, but keep them in a tracked list, so they're out of the way without being lost.
- Put an owner and a deadline on each quarantined test. Without that, quarantine just becomes deletion with extra steps.
- Fix the ones worth keeping. Most flakiness comes from a short, known list of causes — unmocked time, unawaited promises, shared global test state, network calls that should be mocked.

The underlying problem — the team ignoring CI because it's always red — is real and worth solving. But the fix is making CI trustworthy, not making it lie. A green suite that's green because the flaky tests got deleted is worse than a red one you know is red for a documented reason: it turns a visible risk into an invisible one.
