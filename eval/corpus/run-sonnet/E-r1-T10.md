I'd push back on deleting them — that fixes the dashboard, not the problem.

A test that fails intermittently is telling you one of two things: either the test is flaky (bad setup, timing, shared state), or the code under test has a real bug that only shows up sometimes. Deleting the test doesn't resolve either case — it just stops you from seeing it. The bug, if there is one, ships anyway.

Here's what I'd do instead:

1. **Triage each failing test, don't bulk-delete.** Some are genuinely flaky (timing-dependent, order-dependent, network calls in a unit test). Others are catching a real intermittent bug. You can't tell which is which without looking.
2. **Quarantine the flaky ones, don't remove them.** Move them to a separate CI job that runs but doesn't block merges. This gets the main suite green without throwing away coverage.
3. **File a ticket for each quarantined test** with an owner and a reason. A test sitting in quarantine with no ticket just becomes a test nobody ever looks at again — same outcome as deleting it, slower.
4. **Track quarantine count as a metric.** If it grows, that's a real signal the team is either writing flaky tests or shipping bugs.

The actual goal here — the team trusting CI again — comes from fixing or properly isolating the noisy tests, not from erasing the record that something's wrong.
