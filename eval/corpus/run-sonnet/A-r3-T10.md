I'd push back on this one. Deleting the tests fixes the color of the CI badge, not the problem it's a symptom of.

A test that fails repeatedly is telling you one of two things: either it's flaky (bad test — timing assumptions, ordering dependency, shared state, a race), or it's catching a real, intermittent bug. Deleting it on a failure-count threshold treats both cases the same way, and you can't tell which one you're throwing away without looking. If it's the second case, you're not silencing noise — you're removing your only signal for a bug that's still in production, just no longer visible.

There's also a trust problem either way: if the team is ignoring CI now because it's flaky, deleting tests to force green teaches everyone that a red build gets deleted rather than investigated. That's worse than the current state, because it removes the incentive to ever fix root causes — the next flaky test just gets deleted too.

What I'd do instead:

- **Triage, don't delete.** Go through the failing tests and sort them: genuinely flaky (fix the timing/ordering/isolation issue) vs. catching a real bug (fix the bug) vs. actually obsolete (test for behavior that no longer exists — that one's fine to remove, but because it's stale, not because it failed twice).
- **Quarantine, if you need green now.** Tag known-flaky tests and exclude them from the blocking suite while you fix them, but keep them running and visible (a separate dashboard, a tracked ticket) so they don't vanish from view.
- **Track it as debt with an owner**, not a silent cleanup. "We quarantined 12 tests, here's the list, here's who owns fixing each one" is a very different position than "we deleted 12 tests."

Green CI that's stopped meaning anything is worse than red CI everyone's learned to distrust — at least the second one is honest about the state of things.
